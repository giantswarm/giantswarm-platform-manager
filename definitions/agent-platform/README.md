# agent-platform definition

The `agent-platform` capability as data: what a person decides, what the record supplies, what the fleet
policy decides once, and what the definition drops. The render library reads it.

| File | What it is |
|---|---|
| `schema.json` | JSON Schema (draft 2020-12, `additionalProperties: false`) of the inputs: the record under `installation` (read, never typed) and the ten choices, `modelServing.enabled` (default false), the singletons' placement, `scheduling.singletonsCapacity` (`any`, the default, or `on-demand`), the in-cluster MCP backends the network policy fences, `networkPolicy.mcpBackends` (default none), the LLM listener's rate limits, `llmRouting.rateLimits` (default none), with the comment above them, `llmRouting.rateLimitsComment`, how long an idle agent Session and its workspace directory live, `sessions.idleTTL` (default none, the chart's), the portal's AI chat, `aiChat.enabled` (default false) with `aiChat.model` and `aiChat.provider` (`anthropic` or `vertex`, with `aiChat.google.project` and `location`), the portal's skill repositories, `skills.repositories` (default none), the portal's Hive section, `hive.enabled` (default false) with its repositories and board, the managers' commit modes, `clusterManager.github.enabled`, `modelManager.github.enabled` and `agentManager.github.enabled` (each default false), the bots whose posts reach the chat gateway's thread context, `klausGateway.slack.contextBotIDs` (default none), with the comment above them, `klausGateway.slack.contextBotIDsComment`, the bots admitted by their Slack profile name, `klausGateway.slack.contextBotNames` (default none), with the comment above them, `klausGateway.slack.contextBotNamesComment`, the Agent Platform organizations, `organizations.enabled` (default false) with `organizations.apiHostnames` (default none), `organizations.commit.enabled` and `organizations.portal.enabled` (each default false), and the version holds, `versions.chart` and `versions.components.<component>` (each default none), with their reasons, `versions.reasons.chart` and `versions.reasons.components.<component>` (the comment above the hold, default none). Every leaf carries `x-source`, `x-feature` and `x-renders`; a choice carries `x-readback`, the file — one, or several, the first on record holding the key answering — and key it is read back from, and the kind where it is not the key's value (`present`, `host`, `installation`, `comment`, `entries`, `file`). `x-files` names each file's path, `<name>` the installation and `<portalHost>` the installation hosting the portal the platform's portal section is written into, so a portal choice is read back where the section is rendered, whichever installation's plan reads it. |
| `policy.yaml` | The fleet's decisions, keyed by the owning organisation: which components its installations run, the chat gateway's shape, the connector names a target's Dex registers for a hub (the organisation's plain name for the target's first hub of the organisation, the hub's own for every further one; `fromBase` names the organisations whose hubs' connectors the fleet's Dex base registers, which no target renders), the Teleport cluster and the poll interval of every OCIRepository the definition renders (`flux.sourceInterval`) — and, keyed by installation, where a Slack app exists, which is where the gateway runs, with the installation's own default agent, and which stage and organisations run the platform's release candidates. |
| `removals.yaml` | Keys an enabled installation carries today that the definition does not render, each with the reason it is dropped: the template renders it, it becomes a referenced Secret, the platform does not read it, the customer-portal definition owns it, or it is a named migration (M12…) of a former input. A key of kind `kept` is not dropped: its replacement is not on the fleet yet (muster's trusted issuers the shared defaults do not derive, a connector pin, muster's provider token refresh threshold, the kagent controller's and the Postgres instances' on-demand pin, the kagent UI's ingress peer, tuned resources, the installation's own Postgres databases with the kagent controller's mount of its fresh database, kagent's Harnesses, the toolchain-manager's switch and values with the kagent controller's tool image egress origins), so the plan carries it from the record into the render, comments included, and the comparison finds it as defined; the reason says what has to land before the key goes. A removal with `keptWhile` is kept the same way only while the render carries that path: the default ModelConfig's model pin and display name and the inlined ModelConfigs stay while the render carries `kagent.providers`, and go with M43 once it does not. The configmap patch is rendered whole, not edited: a hand-written key no input renders and no `kept` entry names, nested under a rendered block or not, is drift, and a reconcile removes it. |
| `migrations.yaml` | Keys the definition renders that an installation enabled before a migration lacks (a referenced client Secret, the hub's token-exchange client in a spoke's Dex, the portal's Component, the edge's JWT provider, …), each with the migration that adds it: a leaf the record lacks under one of them is a planned change, not drift; so is a comma-separated scalar (kagent's `oidc-extra-audience`) whose only change is entries named as `<path>[<entry>]`. |
| `features.yaml`, `probes.yaml` | The consistency features and their dimensions — a file dimension's key names the files and YAML paths it observes in the grammar the file's header documents, `catchAll: true` marks the kind's dimension for every other leaf, and what no dimension names the verify reports under the feature `other`; the live probes the verify runs. |

## Agent-manager credential operations

`agentManager.githubTokenExchange.enabled=true` configures muster's provider App and confidential RFC 8693 grant-release client for agent-manager. It requires `agentManager.github.enabled=false` and the meta chart `4.177.0` or later, which carries the credential operations contract (giantswarm/agent-platform#1312) and admits agent-manager `2.22.0` and muster `5.61.0` and later only. A `versions.chart` hold below `4.177.0`, a `versions.components.agent-manager` hold with a floor below `2.22.0` or a `versions.components.muster` hold with a floor below `5.61.0` is refused.

The installation's `giantswarm-agent-manager-oauth-client` Secret must already exist in `agent-platform`. The provider App keeps issuer `https://github.com/apps/giantswarm-agent-manager`. The definition generates the `agent-manager-github-broker` client credential; only that client may request the `agent-manager-github` target. The broker accepts subject tokens from this installation's Dex with the portals' audiences and `dex-k8s-authenticator`, the audience of the ID token muster forwards to agent-manager. `dex-k8s-authenticator` is the audience every Kubernetes API token of this Dex carries (kubectl logins, tokens muster forwards or mints for clusters), so every broker client on this muster accepts those tokens as subject tokens: an accepted exception to the MCP rule against token passthrough until agent-manager presents a token issued to itself (giantswarm/giantswarm#39102). Reconciliation adds the render's audiences to the Dex entry on record, keeps the entry's own audiences, and refuses preserved broker configuration with an independent subject-token issuer or without an input-audience allowlist. The entry stays the installation's when the exchange is turned off: `dex-k8s-authenticator` is not removed from it. The definition renders `muster.muster.providerApps`; entries kept only on the record are not preserved.

`agentManager.credentials.uiURL` is optional client-owned input: an HTTPS RFC 6570 URI template with one `{operation}` expression in its path or query, using only `{operation}`, `{parent}` and `{organization}`, and no user information or fragment, matching agent-manager's own validation. The meta chart refuses it unless `agentPlatformOrganizations.enabled` is on. The definition never derives it; unset, no `credentials` block is written. The template and the broker choice are read back from the configmap on record. The manager delivers the link as an MCP URL elicitation to clients that declare it, and as `credentials[].next` text otherwise.

Organization GitOps writes use the meta chart's `agent-manager.tenants.commit` block; `agentPlatformOrganizations` is a separate switch. A client using the HTTPS credential API needs `agentManager.route`. A bundled Flux engine needs `kustomize-controller` in `flux-engine.instance.components` to apply organization Kustomizations.

MCP 2025-11-25 clients keep session capabilities and completion streams in one manager process: keep the released manager chart's single replica (`agent-manager.replicaCount: 1`) while such clients are served.

## The 4 chart line's prerequisites

The 4 line is selected by the record (`agentPlatform.kagentApiV2: true` in `installations/<name>/config.yaml.patch`).
The fleet policy declares the line an organisation's installations run (`chartLine`: `customers` by organisation,
else `default`; none declared leaves the record's line), and the policy grants some organisations a component the 4
line alone carries (the cluster-manager). Where the record selects 3 and either asks for 4, the definition selects the
4 line itself and writes the key into the record as one more file of the configs pull request, keeping every other key
and comment: the record is the installation's own file, edited and never written whole. A fresh enable and a reconcile
of an installation on record alike: the dry run shows the move, the commit applies it, and verify names an installation
whose record is off its line on the runtime feature's `chart-line-on-record` dimension. A line never moves down. An
organisation with an installation that must stay on the 3 line meanwhile is not listed. The
4 line needs, beyond the 3 line's, a cluster that serves `certificates.k8s.io/v1beta1 PodCertificateRequest`: kagent's
Agent Substrate (meta chart 4.49.0 and later) issues each agent's pod certificates through it and distributes its
CA through `ClusterTrustBundle` projected volumes, and the meta chart refuses its install at render time where the
API is not served. That takes Kubernetes 1.35 with the feature gates `PodCertificateRequest`, `ClusterTrustBundle`
and `ClusterTrustBundleProjection` enabled on the API server, the controller manager and every kubelet — a fact of
the cluster App on record, `management-clusters/<name>/cluster-app-manifests.yaml` in the installation's
management-clusters repository, which the plan derives `installation.podCertificateRequest` from:

- the App's values (the ConfigMap its `userConfig` names) carry the three gates enabled in each of
  `cluster.internal.advancedConfiguration.controlPlane.apiServer.featureGates`,
  `.controlPlane.controllerManager.featureGates` and `.kubelet.featureGates` (entries of
  `{name, enabled, minKubernetesVersion}`; a list on record replaces the chart's default list, so it carries every
  gate the component needs), or
- for a component whose list the record does not set, the App's chart enables them by default: the cluster chart
  8.3.0 and later ([giantswarm/cluster#1005](https://github.com/giantswarm/cluster/pull/1005)), which the provider
  charts ship from `cluster-aws` 10.3.0, `cluster-azure` 9.3.0 and `cluster-cloud-director` 7.3.0 (the table in
  `substrate.go`; a chart not in it — `cluster-vsphere` until it releases the pin, `cluster-eks` — counts only where
  the record sets the gates). The chart's version is the App's `spec.version` where it pins one; a release-based
  App — every CAPA and CAPZ management cluster — pins none and names its release in the values
  (`global.release.version`), and the version is the one that release lists for the chart in
  [giantswarm/releases](https://github.com/giantswarm/releases) (`<provider>/v<release>/release.yaml`, read as the
  person). A release that cannot be read or lists no such chart leaves the fact `false` with the reason on the
  report; the installation stays readable and the comparison runs.

With kagent rendered on the 4 line and the fact `false`, the plan refuses — `installation.podCertificateRequest: …`
naming the gates, the path and the charts — and the dry run says a commit would be refused (`commitRefused`); the
3 line renders whatever the fact says. With the fact `true`, the runtime feature's live dimension
`live-pod-certificate-request` discovers the API through the installation's apiserver: served, as defined; while
the control plane and the nodes still roll after the gates were set, the check reads `rolling: …` and the feature
is marked, the meta chart's install waiting for the same API.

On CAPZ the 4 line also needs two facts in the installation's record that the definition never writes: the shared
configuration renders the Substrate snapshot store's Workload Identity
(`kagent.harness.snapshotStore.crossplane.capz`) from `provider.azure.subscriptionId` (the subscription of the
management cluster's AzureCluster, `spec.subscriptionID`) and `provider.azure.oidcIssuerUrl` (the API server's
service-account issuer, the `issuer` of its `/.well-known/openid-configuration`, AzureCluster
`status.oidcIssuerProfile.issuerURL`), and the meta chart refuses its install without them. The shared default
carries both empty, so each CAPZ record sets them in `installations/<name>/config.yaml.patch`. Where kagent runs on
the 4 line and the record leaves one empty, the comparison still shows every difference and the commit is held:
`missingFacts` lists the keys, and `commitRefused` names the record, each key and where its value comes from. A
provider without such facts (capa) holds nothing.

Credentials are generated by the engine as SOPS-encrypted Secrets under `extras/agent-platform/secrets/`, every
value named per installation so that no secret is ever shared between installations or organisations (the
portals' Dex client id is the constant `backstage`; a portal that still signs in through another client is trusted by that client's id as well); every Dex client is
a referenced Secret in Dex's namespace (dex-app 3.2.0 or later; next to a hand-made inline secret, which an installation enabled by hand still carries, 3.2.2). The portal's client Secret
`dex-client-backstage` is not this definition's: the customer-portal definition renders it into the portal's directory
(`extras/backstage/backstage/dex-client-backstage-secret.enc.yaml`), a hand-kept portal keeps it by hand, and this definition's
dex patch entry references it by name and renders no file for it — so on an installation with both capabilities no repository
path and no Kubernetes object is rendered by two definitions. That is a prerequisite of the plan: with `installation.dexAppVersion` on record older than 3.2.2 (2.4.0 on the 2.x line), the comparison still shows every difference and the commit is held — `commitRefused` names the version, the file it was read from and the collections kustomization to pin `dex-app` in first; an empty fact holds nothing. The other prerequisite is the layout of the installation's Dex values: app-operator merges the plaintext configmap patch with the encrypted secret patch (helm-controller its `valuesFrom`) by replacing a list, never by appending, so an `oidc.extraStaticClients` or `dexK8SAuthenticator.trustedPeers` list the encrypted values still carry stands whole over the one this definition renders and the platform's clients never reach Dex. With `installation.dexSecretLists` naming such a list, the comparison still shows every difference and the commit is held — `commitRefused` names the encrypted file, the lists with their entries and the rendered clients and peers they would shadow; the engine never edits the encrypted file, so a person carries every entry over first — each hand-registered client to its own Secret and a plaintext entry the plan keeps, each peer and each connector to the plaintext list — and drops the lists from the encrypted values (`removals.yaml`, M1); the customer's connectors list (`oidc.customer.connectors`) is held the same way where the encrypted values carry it and the render declares a token-exchange connector. What a person supplies at commit is
named by field and follows the policy, the record and the choices: the Slack app's `klausGateway.slack.bot-token` and
`signing-secret` where the gateway runs, plus its `app-token` where the installation is private (socket mode), and
the chat's credential where the portal runs the chat and the Component carries it — its Anthropic API key
`aiChat.anthropic.apiKey` (supplied raw, written base64-encoded into the Secret: the chart copies the value under its secrets Secret's `data`, which Kubernetes takes base64-encoded), or on Vertex AI the service account's JSON `aiChat.google.credentialsJson`; not where the
portal's own app-config carries the chat by hand —, nothing else — an installation without a Slack app or with its chat
by hand commits with no supplied secret.
No model key is ever supplied. Where the meta chart still takes kagent's model provider, kagent references the
Secret `kagent-anthropic-key` (key `ANTHROPIC_API_KEY`, namespace `kagent`), which the definition renders no file
for; from 4.175.0 on the definition references no key at all. Adding a ModelConfig with its key Secret (in the
portal, or as an object under `extras/agent-platform`), or creating that Secret where the patch still references
it, is the model action the plan names for the installation's people: until some ModelConfig in `kagent` resolves
its key, the verify reads the runtime feature as *waiting for the customer* rather than drifted. On the 4 line the
other is `agent-models`: every Agent in any namespace that still names `default-model-config` (live dimension
`live-agent-models`, each listed with the HelmRelease that renders it) is moved to a ModelConfig of its
namespace before the installation runs 4.175.0, which renders no `default-model-config`.

Key paths in `x-renders` and `removals.yaml` are normalised: a list index is `[*]`, a per-installation map key is
`<name>`. A path covers every key beneath it.
