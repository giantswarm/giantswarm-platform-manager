## [Unreleased]

### Added
- A generated value rotates on request ([#278](https://github.com/giantswarm/giantswarm-platform-manager/issues/278)). A value rotated only as a side effect of a file that had to be written, so a credential that had to be replaced (a suspected exposure, a departing operator, a scheduled rotation) was rotated by hand, outside the engine, and the second person approving saw a rotation only as a by-product of another change. `reconcile_capability` (and `enable_capability`, which shares its plan) takes `rotate`, generated values by name as the plan lists them (`generatedSecrets[].name`), and `platformctl installation reconcile … --rotate <name>` (repeatable) passes it. The dry run lists each one `rotates` with `forcedBy: "request"` and the files on record it is frozen in, those files as *update*; the commit draws a new value, rewrites every file that holds it and draws the credentials revision of the component that owns it, so every workload that reads it restarts: the definition names, next to the revision it renders, the revision of every value of the Secrets that hold it (`render.Result.Revisions`) — muster's Dex client secret, registration token, OAuth encryption key and Valkey password roll on `<installation>-muster-credentials-revision` (4 line), each MCP server's credentials on its own. Names carry their installation: over a set a name applies to each installation whose plan lists it, and one no plan lists is refused by name before anything is written, like one frozen in a file with other owners. The Action records the names asked for (`spec.rotate`), the review names them (*rotates on request: …*), and the change, the pull request and `platformctl` name them apart from the rotations a file forced. dex-k8s-authenticator's client secret is not a generated value (it lives in the dex-app encrypted patch the manager does not write) and cannot be rotated this way yet.

### Fixed
- A wave refuses a generated value frozen where it cannot rotate, as a commit of one installation does ([#273](https://github.com/giantswarm/giantswarm-platform-manager/issues/273)). The wave's pre-check skipped `FrozenRefusal`, so a wave over a set whose plan froze such a value would have opened the pull requests the same change, committed for one installation, refused. The single commit, the wave's pre-check and the dry run's `commitRefused` now take the plan's refusals — the dex-app on record, the frozen values, the hub's Dev Portal — from one list, and a test holds the three to it.
- Moving a hand-kept portal onto the `customer-portal` definition no longer takes the platform's section from the running portal ([#275](https://github.com/giantswarm/giantswarm-platform-manager/issues/275)). The commit replaced the literal extension list with the shared list without the platform's section (`#extensions`) and dropped the section's keys as moved into the Agent Platform Component's fragment, but on a hand-kept portal the fragment carries its object-shaped keys alone: the AI chat and the Agent Platform page (`page:ai-chat`, `api:ai-chat/service`, `api:ai-chat/drawer`, `app-root-element:ai-chat/drawer`, `page:agent-platform`, `nav-item:agent-platform`) and the muster registry were gone until an agent-platform reconcile, and `agentPlatform.skills.repositories`, which no definition rendered, emptied the skill catalog for good. The portal's app-config now keeps the section as the record carries it and includes the list with it (`#extensionsAgentPlatform`, `#extensionsAgentPlatformAiChat` with the chat, each with its `GrafanaDashboards` pair) until the fragment on record owns the portal's lists (`platformSection`, read from the portal's app-config and the fragment on every comparison), and the `agent-platform` definition renders the skill repositories as a third choice, `skills.repositories`, read back from the fragment, else from the portal's own app-config. A migration is three actions — the customer-portal commit, the agent-platform reconcile that takes the lists over, the customer-portal reconcile that hands the section over, planned as *Moved* — and the portal keeps its extensions and skill repositories at every step. `agentPlatform` is handed over by key (`kagent`, `skills`, `fluxServiceAccountName`), and a test holds every `other-definition` removal to a key the `agent-platform` definition renders.
- A rotated muster credential restarts every workload that reads it, and a stage whose workload is left unready reads *failed* ([#274](https://github.com/giantswarm/giantswarm-platform-manager/issues/274)). The credentials revision reached muster and its Valkey only, while klaus-gateway reads muster's Valkey password (`KLAUS_GATEWAY_VALKEY_PASSWORD`) and the agent-manager, cluster-manager and model-manager read the platform client's secret from `muster-oauth-credentials` (`DEX_CLIENT_SECRET`), each once at start: after a rotation klaus-gateway kept the old password and turned unready until restarted by hand, and the action read *enabled*. The definition keeps the consumers of muster's credentials in one list (`musterConsumers`); on the 4 line the platform patch hands each consumer that runs the revision through `components.<name>.valuesFromRefs` — the gateway and the managers onto the pod annotation `muster-credentials-revision` — and the runtime feature reads each consumer's Deployment Available (`live-platform-workloads`: muster, `muster-valkey`, and klaus-gateway, agent-manager, cluster-manager and model-manager where each runs). The render-consumption test renders the chat gateway's shape too and holds the list to the charts: every workload whose pods read either Secret is a running consumer's Deployment, and the revision changes its pod template. Installations already on M37 read the new refs as planned (M38); the first commit after this release restarts the gateway and the managers once, as the annotation appears.
- The Dex client probes read *drifted* for a client Dex does not know and for a redirect URI not registered for the client ([#268](https://github.com/giantswarm/giantswarm-platform-manager/issues/268)). `dex-auth-request`, `live-dex-auth-per-client` and `live-dex-auth-portal-client` asked Dex's `/auth`, which only picks the connector and answers any client id and redirect URI alike: its connector picker (200) with several connectors, a redirect to `/auth/<connector>` (302) with one. So a made-up client read *as defined* on every installation checked. The probes now take the connector step: they request the `/auth/<connector>` that Dex's own answer names (the redirect's location, or the picker's first connector link), whose handler validates the request, and hold its answer. A redirect to the identity provider, or a password connector's form, is *as defined*; 404 (an unknown client) and 400 (a redirect URI not registered for the client) are *drifted*, and the result names the connector, the client and, for 400, the redirect URI.
- A `customer-portal` commit no longer strips the hub's Dev Portal. The definition renders a customer's portal only, and its removals dropped every section of the hub's portal: its Postgres database (the catalog would restart on the in-memory database), the pages it serves over muster, its incident links, CircleCI proxy, scaffolder, GitHub and registry access. A dry run over the hub planned all of that with `commitRefused` empty, so a commit, or a wave whose set includes the hub, opened the pull request and only the reviewer stood in the way. Those removals now have their own kind, `hub`. A commit whose plan removes one that the record carries with a value is refused for the installation: `commitRefused` names the sections by file, the dry run's new `hubSections` lists their keys, and a wave over a set with that installation is refused whole, like the dex-app refusals. The comparison still plans every removal. A section on record without a value (`scaffolder: null`) and an installation entry the portal does not federate (`gs.installations.<name>`) go without a refusal. Until the hub's shape is an input of the definition, the hub's portal is kept by hand ([#269](https://github.com/giantswarm/giantswarm-platform-manager/issues/269)).
- `platformctl self-update` replaces the binary with a single rename (`selfupdatecosign.Install`). go-selfupdate's swap renamed the binary to `.platformctl.old` before it moved `.platformctl.new` in, so a `platformctl` started in between found no binary. Two updates at once shared those names, and one could remove the binary the other had just installed. Now a `platformctl` started meanwhile runs the old binary or the new one, any number of updates can run at once, and the binary keeps its mode.
- A stage whose Dex has not read a rotated client secret reads *failed*, naming the client. Dex reads a referenced client secret into its environment only when its container starts. dex-app 3.2.3 restarts the container when the Secret changes; before 3.2.3 nothing does, so after a rotation Dex kept the old secret, the client's sign-ins failed with `invalid_client`, and the watch still read the stage *enabled*: `live-dex-auth-per-client` asks `/auth`, which answers the same for either secret. On two test installations this let a wave go on with the MCP servers' sign-ins broken. Both definitions now render a live probe of the new kind `SecretLoaded` per client Secret their dex patch references (`live-dex-client-secrets-loaded` for muster, the MCP servers, kagent, the portal and the hubs' token-exchange clients; `live-dex-portal-secret-loaded` for the portal). The probe holds every running Dex container's start against the time the managed-fields entry that owns the Secret's data last changed. It reads that time through the new `Manifest` shape (mcp-kubernetes's `full` output), never the value: mcp-kubernetes masks every Secret value, so a token-endpoint check with the secret cannot run as the person ([#252](https://github.com/giantswarm/giantswarm-platform-manager/issues/252)).
- A rotated muster credential reaches muster and its Valkey. The `agent-platform` definition rotated `muster-oauth-credentials` and `muster-valkey-credentials` like the servers' Secrets, but nothing rolled the pods reading them: muster reads both Secrets at start (the muster chart carried `checksum/config` only until 5.31.1) and its Valkey reads the users Secret once in its init container. The definition now renders muster's *credentials revision* the way it renders the servers' (M35): one generated value (`<installation>-muster-credentials-revision`) held by `muster-oauth-credentials` (`credentials-revision`), `muster-valkey-credentials` (`revision`) and a third Secret `muster-credentials-revision` in the Flux namespace, which the platform patch hands to the muster and valkey HelmReleases through the meta chart's `components.<name>.valuesFromRefs` (`valuesFrom` entries with `targetPath` onto `muster.oauth.server.existingSecretChecksum`, `muster.oauth.server.storage.valkey.existingSecretChecksum` and `valkey.auth.usersExistingSecretChecksum`), which muster 5.31.1 and valkey-app 0.1.5 render as pod annotations. A rewrite of either credentials file draws the revision anew and rolls both pods; a reconcile without a rotation changes nothing. The first commit after this release adds the revision key to both Secrets on every installation, which rotates muster's credentials once (`rotates` in the dry run, forced by the credentials file). muster's schema is closed, so the render-consumption test pins muster at 5.31.1, the first release with the keys; the meta chart's range floats every installation there. ([#230](https://github.com/giantswarm/giantswarm-platform-manager/issues/230))
- The `helm.sh/chart` label is valid for any chart version ([#243](https://github.com/giantswarm/giantswarm-platform-manager/issues/243)). The label is `<name>-<version>` cut to 63 characters, and the cut of a long version (a branch build's `X.Y.Z-dev.<branch>.<date>.<time>.h<sha7>`, or the `<tag>+<digest>` helm-controller installs) could end in `_` or `--.`, which trimming one `-` and one `.` left in place, so the API server refused every labelled object; the whole run of `-`, `.` and `_` at the ends of the cut is now trimmed, and a render proof in `internal/chart` checks the label for such versions.
- A changed portal fragment restarts the portal. The `agent-platform` definition's portal Component mounts its app-config fragment (`agent-platform-app-config-backstage`) through `backstage.extraAppConfig`, and Backstage reads the file at start. A changed fragment reached the cluster, but the portal's HelmRelease saw no change and the pod kept the old configuration until someone restarted it. The Component's values now carry the fragment's sha256 as the entry's `checksum`, which the portal's chart (backstage 2.60.2 or later, giantswarm/backstage#2577) renders as a pod annotation, so the fragment and its checksum change in one commit and the upgrade rolls the portal. A portal whose chart line resolves to an earlier chart gets no checksum, since that chart's schema refuses the key (M36).
- A rotated MCP server credential reaches the running server and its Valkey. When a commit rotated a server's generated credentials (the plan's `rotates`), the manager wrote the new values into `extras/mcp-<name>/oauth-credentials.enc.yaml` and `valkey-credentials.enc.yaml` and Flux applied the Secrets, but nothing rolled the pods reading them: the server loads its Secret at start (`envFrom`, or key by key) and its Valkey reads the users Secret once in its init container, and no pod template carried a mark over either Secret — on graveler on 2026-09-22 both kept the old values until an operator restarted them, and in between the server disagreed with Dex and with its Valkey ([giantswarm/mcp-prometheus#302](https://github.com/giantswarm/mcp-prometheus/issues/302)). The charts now render a checksum annotation from a value the definition hands them (`app.oauth.existingSecretChecksum`, `mcpKubernetes.oauth.existingSecretChecksum`, `oauth.existingSecretChecksum`, the keyed charts' `…oauth.storage.valkey.existingSecretChecksum`, the Valkey chart's `valkey.auth.usersExistingSecretChecksum`), and the `agent-platform` definition renders that value as a *credentials revision* per server: one generated value (`<installation>-mcp-<name>-credentials-revision`, 32 alphanumeric characters, no secret) held by the server's credentials Secret (`CREDENTIALS_REVISION` where the chart loads the Secret with `envFrom`, `credentials-revision` where it reads keys), by its Valkey's (`revision`) and by a third Secret `mcp-<name>-credentials-revision` in the Flux namespace (`credentials-revision.enc.yaml`), which the server's HelmRelease and its Valkey's read into those chart values through `valuesFrom` entries with `targetPath` (kustomization patches over the fleet base; the Valkey release's list is created, the server's appended after the fleet's and the user values' sources). The frozen model does the rest: a rewrite of either credentials file gives the revision a new value and rewrites every file holding it, so the roll follows the commit that rotates, and a reconcile without a rotation keeps the revision and changes no pod template. The first commit after this release adds the revision key to both credentials Secrets on every installation, which rotates every server's credentials once (the plan says so: `rotates`, forced by the credentials file), and the pods roll with it. The Valkey's roll also needs the fleet base's Valkey release to read its users Secret ([giantswarm/management-cluster-bases#764](https://github.com/giantswarm/management-cluster-bases/issues/764)) and the Valkey chart's mark ([giantswarm/valkey-app#72](https://github.com/giantswarm/valkey-app/issues/72)); the definition renders the mark at the chart's value either way. ([#212](https://github.com/giantswarm/giantswarm-platform-manager/issues/212))
- `platformctl` waits for muster's CLI bridge to register its tools before the first call. `muster agent --mcp-server` answers `initialize` before it has connected to the aggregator, so a call sent at once was refused with `tool 'call_tool' not found` — on every call while the aggregator was slow to answer. The session now polls the bridge's tool list for `call_tool` (up to 20 s, every 250 ms) and names the bridge when it never appears.
- A commit of one installation asks for a supplied value only where it writes the file that holds it. `enable_capability` and `reconcile_capability` with `installation` demanded every value the definition names as supplied (`platformctl installation reconcile graveler customer-portal --commit`: the GitHub App's five values and the token broker's two) although the encrypted files holding them stood on record unchanged and a secret file on record is never generated again — so the person would have re-supplied seven values the commit writes nowhere, while a wave over the same installation rendered them as markers and proceeded. The plan now splits the definition's supplied fields by their files: a field whose files all stand unchanged is `suppliedOnRecord` (the dry run says "Supplied values on record: … their files stand, nothing to supply"), rendered as its marker at commit and written nowhere; `suppliedSecrets` names only the fields in a file the commit creates or rewrites, or in no file of the plan, and the commit refuses one missing and one supplied that is on record. The wave keeps its rule with the same split: a target with a field to supply is refused before any write, naming the files not on record as rendered.
- The chat's Anthropic API key lands in the Component's Secret base64-encoded. The `agent-platform` definition wrote the key supplied at commit (`aiChat.anthropic.apiKey`) into `agent-platform-ai-chat-credentials-backstage` as it was, while the backstage chart copies the chart value `anthropic.apiKey` under its secrets Secret's `data`, which Kubernetes takes base64-encoded — a raw key supplied as the README asked would have made the Secret fail to apply and the portal's HelmRelease with it; a hand-kept portal carries the key base64-encoded in its user secrets for the same reason. The render now encodes the supplied key as the `customer-portal` definition encodes every value the chart copies this way (`render.Base64Leaf`, shared; a marker stays a marker); the key is supplied raw as before.
- The `agent-platform` definition renders a hub's token-exchange client under the id the hub presents. It named the client `<hub>-token-exchange` on both sides — in the target's Dex and in the hub's credentials Secret `<target>-token-exchange-credentials` — while the fleet's live client is `muster-token-exchange-<target>`, registered by hand on every installation the hub brokers into, and the hub's credentials on record carry that id and its secret. Both leaves are encrypted, so the plan compared the hub's file as kept (the same skeleton) and never saw the id differ, and the target's plan added a second client `<hub>-token-exchange` with a fresh secret nobody presents: the first wave's dry run showed it on graveler and glean, graveler's reconcile added it, and a later removal of the hand-registered client would have broken the federation. The definition adopts the fleet's id: `muster-token-exchange-<target>` for the registry's hub, `muster-token-exchange-<target>-<hub>` for every other hub (a target's Dex registers one client per hub, and only one can carry the plain id), rendered on both sides from the same two facts — the target and whether the hub is the registry's (`installation.hub` on the hub, the new registry fact `installation.federation.registryHub` on the target). The generated client secret is named after the client, `<client>-client-secret`; the target's Dex client Secret is `dex-client-muster-token-exchange-<target>[-<hub>]`, the file graveler already carries by hand. The hub's credentials files stay kept, nothing rotates, and a target's reconcile renders the client the hub presents and no second one; the M32 migration keys name the new id. The alternative, reading the id back from the hub's record, was not taken: the id sits under `stringData` of a SOPS-encrypted Secret, the manager decrypts nothing, and muster reads the id and the secret from the one Secret, so the id cannot leave the encrypted file without a muster change.
- A dry run says what a kept encrypted file holds that the comparison could not see. A secret file on record is kept when the render changes nothing outside its encrypted values, and a literal the render puts under an encrypted field — a client id beside a generated secret — is compared against nothing, so a file whose id differs from the render read *unchanged* without a word. The plan's file now carries `unseen`, the literals under the record's encrypted fields with the render's value (`stringData.client-id: muster-token-exchange-graveler`), `platformctl` prints them under the file table, and the README says the value on record stands whether or not it is the render's.
- A set's dry run answers within the call. `reconcile_capability` over a set (`platformctl installation reconcile <a> <b> … --dry-run`, `--all`) answered every installation's comparison with its evidence — the differences of every dimension and the files each was compared in, three quarters of the document — and the rendered content of every file by default, so the answer grew with the fleet: three installations were 553 KB, with content 926 KB, the whole registry — fourteen installations on record — above 2 MiB. The path to a person has a cap the manager never saw: the gateway in front of muster buffers a tool's answer whole and drops one above 2 MiB — muster's `call_tool` wraps the manager's text once more on the way — with `body exceeded buffer limit`, naming neither the size nor the limit; measured on 2026-09-22 against the manager v0.34.0 the three-installation dry run answered nothing at all until the client's own five-minute timeout. A set now answers each installation's plan with the comparison rolled up — every dimension with its mark and reason, none of the evidence — and no file content unless `content: true`; the three installations answer at 209 KB, with content 581 KB. One installation's dry run (`installation`, alone; `platformctl installation enable|reconcile <one>`) carries the evidence and the content as before, as `verify_capability` does: a set names what deviates, one installation shows it. And every tool answer is bounded at 1 MiB (`tools.AnswerLimit`): one above it is refused naming its size, the limit and how to ask for less — a smaller set, one installation, no content — instead of being lost between muster and the person.
- An action's pull requests merge in the order the files reference each other, not by repository kind. The order was configs before management-clusters before teleport-fleet, yet the `agent-platform` definition renders a Dex client with a `secretRef` into the configs repository's dex-app patch and the client's Secret into the management-clusters repository — on dex-app 3.2.2 a referenced client is a `secretKeyRef` environment variable on the Dex pod, so between the two merges Dex could not start — and the tunnelport release and the RemoteApps name Teleport tokens that teleport-fleet's pull request creates, the last in that order; the first wave over graveler was merged by hand as teleport-fleet, management-clusters, configs to avoid it. Now a pull request whose files create an object another pull request's files reference merges before it: the Secrets its manifests declare and the tokens its tunnelport values list, against every `secretRef` (of any spelling), `existingSecret`, `secretName` and `tokenName` the other's files carry; a file on record that carries the object already creates nothing. The plan's `pullRequests[].order`, the review's list, the pull requests' bodies and `merge_action`'s stage order carry the same order, each pull request naming the ones it follows and why (`pullRequests[].after`), every file what it `creates` and `references`. Among pull requests no reference orders, the repositories' kind stands as before; a fresh enable, every file new, merges management-clusters before configs, and teleport-fleet before both where a private target is tunnelled.
- The `agent-platform` definition renders the output cap of kagent's default ModelConfig, `kagent.providers.anthropic.config.maxTokens: 32000`, on every installation that runs kagent. kagent's default of 8192 tokens is shared by the model's adaptive thinking and its visible answer, so a long investigation's answer was cut mid-sentence once the thinking had used most of it; 32000 is about six times the largest complete call observed and bounds a runaway call to roughly 6.5 minutes and $0.32. The bound follows from how the platform calls the model — the same agents through the same edge on every installation — so it belongs to the `config` map the definition already renders (`baseUrl`): not to an installation's choice, and not to the shared defaults, which carry the default model and no call parameter. The one installation carrying the cap by hand read the leaf as drift on the `runtime` feature's `kagent-providers` dimension, and a reconcile would have dropped it. An installation without the leaf reads it as the planned addition M34 (`migrations.yaml`), landed by its next reconcile.

- `platformctl installation verify` no longer loses the live half to the muster CLI bridge's deadline, and a live half that ends without an answer names the layer that cut it. The bridge (`muster agent --mcp-server`) waited 5 minutes for every call whatever `--timeout` said, and lost the hub's live answer behind a notification muster wrote onto the call's response stream ([giantswarm/muster#1309](https://github.com/giantswarm/muster/issues/1309), fixed in muster's bridge): the manager's log showed `verify_installation` done in seconds, the gateway in front of muster the call completing with HTTP 200, and `platformctl` reported `liveError: x_giantswarm-platform-manager-live_verify_installation: Meta-tool execution failed: tool call failed: transport error: context deadline exceeded` after 5 minutes, with `--timeout 12m` as with `--timeout 25m`. `--timeout` now bounds each call in the bridge and in platformctl alike: the session sends it as `call_tool`'s `timeout` argument, so the bridge waits as long as platformctl does (its own bound is `--timeout` plus 15 s, so the bridge's deadline arrives first), the repository half and the live half each have the whole of it, and the bridge is no longer started under a context the calls share. A call that ends without an answer is a `Cut` that says who gave up — the bridge (`cut by the muster CLI bridge, which got no answer from muster within its call timeout of 5m0s; muster and the manager may well have answered`), muster (`the registration's timeout`, its `spec.timeout`) or platformctl (`whose --timeout ran out waiting for the bridge to answer at all`) — printed on the `Live:` line and, with `--output json`, as `liveError` plus `liveCut: {layer, tool, timeout}`. ([#198](https://github.com/giantswarm/giantswarm-platform-manager/issues/198))
- A portal whose own app-config carries the AI chat by hand no longer stops a wave. v0.38.0 made the chat's key a value supplied at commit wherever the chat is on, and a wave carries no supplied value — so the first real wave over graveler, glean and gazelle, whose portals carry the chat by hand (the key in their user secrets), was refused whole before any write: `needs the supplied value(s) of aiChat.anthropic.apiKey … ai-chat-credentials.enc.yaml not on record`. The refusal is the engine's rule and stands; the definition asked for a key the portal supplies already. `installation.portals[*].handKeptChat` is a registry fact of the portal, read from its app-config on record (the `aiChat` block), never typed, as `handKept` reads the extension list: where it is true the Component renders the chat's blocks — the same fragment — and no credentials Secret, lists no such file and asks for no value, so the portal's environment keeps the key as the portal keeps its lists, and a wave reconciles the portal. The key becomes the Component's when the hand-kept block goes (the `customer-portal` definition's planned move): the Secret and its kustomization entry are then the planned addition M18, supplied through an enable of that installation alone with `aiChat.anthropic.apiKey`. The `hand-kept-portal` golden shape carries its chat by hand and supplies nothing at commit.
- A commit no longer needs a `.sops.yaml` in a repository it writes plain files into. The commit step read every target repository's `.sops.yaml` before writing, and refused the whole action without one — so the first wave's commit over graveler failed at `giantswarm/teleport-fleet`, whose only file in the plan is the plain tunnelport values file (`reconcile-wave-5dfhvz`: failed, no pull request open), although no secret is ever written there. Now a repository without a `.sops.yaml` gets plain files as they are, and only a file carrying a generated value refuses the commit, naming the file and the `.sops.yaml`; a repository with one is encrypted as before.
- A reconcile keeps what the shared defaults do not carry yet. The `agent-platform` definition's removals named seven keys as migrations to the shared defaults or to objects under extras — muster's `trustedIssuers` (M15: the cluster's service-account issuer kagent's agents present, and on a private installation the Dex entry with its subject claim and audiences), the kagent UI's `oauth2ProxyIngress` (M22: the peer the Dev Portal's tunnel reaches the UI through), muster's pinned login connector (M27: glean's Dex has no `giantswarm-github`), muster's and the kagent controller's `resources` (M23), kagent's inlined `modelConfigs` and default `model` (M25, M26) — and the first wave's dry run over graveler, glean and gazelle rendered every one of them removed, while shared-configs still carries the trusted issuers commented out, no ingress rule and one connector for every Giant Swarm installation, and gazelle has no ModelConfig objects under extras: merged, kagent's agents would have lost muster on all three and the Dev Portal glean. These removals are of kind `kept` now: the plan carries the key from the record into the render, comments included, the pull request never removes it, the comparison finds it as defined instead of planned, and the reason says what has to land before the key goes; `agent-platform-mcps.defaults` (the keep policy of the MCPServer objects, the handle of M19) is kept the same way. The chat gateway's `klausGateway.reviews.allowedCallers` keeps the callers on record beyond the policy's, after them, like the audience lists: gazelle names Shield's, Planeteers' and Honey Badger's sweeps, which the policy does not.
- The rollout watch judges a stage by what the action committed, not by the definition of the day. `watch_action` renders the action's inputs on record with the definition of the manager's current version and holds the live values against that render, so a definition released between the action's commit and its watch that adds a rendered leaf — the first wave's action over graveler, committed on v0.38.1 on 2026-09-22 and watched on v0.40.0 after its HelmReleases were resumed, met M34's `kagent.providers.anthropic.config.maxTokens` from v0.39.9 — read one difference on `live-drift` and `live-kagent-provider-values`, for a value the action never asked for and Flux never had, and marked the stage *failed* while the same call's record half read the same leaf as the planned addition M34. The live half now reads a rendered leaf the installation lacks under a key the capability's migrations name as the planned change it is on the record — the definition's own `configmap:` keys, read under the installation's facts, so both halves give one difference one mark — and a scalar merged as a set whose only change is entries the migrations add the same way; a leaf the installation holds with another value, or lacks under no key, stays drift. ### Changed

- The live surface trusts a list of token audiences: the chart value `live.audiences` (list) replaces `live.audience` (string; removed, the chart is 0.x), and `muster.liveServer.requiredAudiences` renders `spec.auth.requiredAudiences` on the live `MCPServer` — the audiences muster requests at login, so every forwarded token carries them whichever client the person signed in with. The server trusts the union of the two lists (`LIVE_AUDIENCES`, `--live-audiences`, comma-separated); an empty union refuses to render and to start the live surface, since an empty list would accept every audience. `get_info.live` reports `audiences`. A person's ID token names the client they signed in with — the platform's own, a developer portal's — so a hub with several sign-in clients accepted only one of them before.
- The managed model key of kagent is rendered as `secrets/kagent-anthropic-key-secret.yaml` (the Secret keeps its name `kagent-anthropic-key`): a secret file's name carries `secret` or `credential` so that the commit encrypts it.
