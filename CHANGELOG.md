## [Unreleased]

### Fixed

- The `customer-portal` definition renders `NODE_EXTRA_CA_CERTS` with the tunnel. With `tunnel.enabled` it rendered the SPIFFE bundle's ExternalSecret, store and reader and the volume and mount that put `svid_bundle.pem` under `/app/tunnelport-spiffe-bundle`, but no `backstage.extraEnvVars` entry for it; Node reads extra CA certificates through `NODE_EXTRA_CA_CERTS` alone, so the mounted bundle was inert and the backend did not trust the SVIDs the tunnel Services present, and a reconcile would have dropped the variable the portals carry by hand. `backstage.extraEnvVars` is one list Helm replaces wholesale across the HelmRelease's values sources (the shared base's default, the portal's user-values, the agent-platform Component's values), so the portal's user-values now own it whole: the installation's avatars host as the CSP image source (`BACKSTAGE_AVATARS_IMG_SRC`) with the platform enabled, `NODE_EXTRA_CA_CERTS` on the bundle with the tunnel on, no list without either so the shared base's `'self'` stands. The `agent-platform` definition's portal Component sets no `extraEnvVars` any more, on a hand-kept portal or a rendered one; `removals.yaml` no longer moves the avatars entry to the Component, and the key is attributed to `tunnel.enabled` and `installation.agentPlatform`.
- The portal's Dex client Secret `dex-client-backstage` has one owner. On an installation that hosts a portal and runs the agent platform, both definitions rendered the Secret, each into a file of its own — the `customer-portal` definition's `extras/backstage/backstage/dex-client-backstage-secret.enc.yaml` and the `agent-platform` definition's `extras/agent-platform/secrets/dex-client-backstage-secret.yaml`: two files declared one object, a reconcile of both capabilities wrote it twice, and the two renders could only stay equal by accident. Now the `customer-portal` definition renders the Secret, and the `agent-platform` definition references it by name in its dex patch entry (`render.PortalDexClient` builds the entry for both) and renders no file for it: its secrets kustomization no longer lists one, and the M30 migration keys for the file are gone, so an installation's agent-platform card plans no such file. A test holds the two definitions to disjoint filesets over one installation that hosts a portal and runs the platform: no repository path and no Kubernetes object rendered by both.
- `verify_installation` reaches the installation's kubernetes tools through muster again. muster routes a family's tool (`x_kubernetes_get` with `management_cluster`) to the member whose *server name* the instance argument carries, and the loop-back passed the installation's name — muster refused every read with `tool x_kubernetes_get is not available on server "<installation>" (available: <installation>-mcp-kubernetes, …)`, so every live dimension but the HTTP probes read *not checked* for everyone. The member's name is `live.muster.kubernetesMember`, a template over `{{ .Installation }}` with the platform's `{{ .Installation }}-mcp-kubernetes` as default (`LIVE_KUBERNETES_MEMBER`); `get_info` reports it under `live.kubernetesMember`. The e2e fake muster takes the server name the way muster does.
- The `agent-platform` definition's portal Component sets none of a portal's lists where the portal is hand-kept, and the fact is read from the record, not typed: `installation.portals[*].handKept` is true where the portal's app-config carries a literal `app.extensions` list of its own, false where it includes the shared list the customer-portal definition renders. Backstage and helm-controller replace lists across config files and values sources, so on such a portal the Component writes its object-shaped keys only (`agentPlatform.kagent.installations.<name>`, `backstage.extraAppConfig`) and leaves `app.extensions`, `muster.installations` and `backstage.extraEnvVars` the portal's; before, only the registry's hub was spared, and a Giant Swarm-owned installation with a hand-kept portal of its own would have lost the portal's extension list, gained a muster entry and had its environment cut to the avatars host. The day the customer-portal definition renders the portal the fact reads false and the Component carries the lists. The section lands in the installation's own portal first — before, "the organisation's first portal" put a non-hub installation's section into the hub's tree, replacing the hub's own Component; else in the organisation's portal on a sibling that is not hand-kept; a hand-kept sibling portal, the hub's Dev Portal, takes no other installation's Component. A golden shape `hand-kept-portal` holds the render; the Slack-app goldens move the Component into the installation's own tree or render none.

### Added

- The `agent-platform` definition names the connector of a token exchange per hub and target. A target's Dex registers one connector per hub whose muster brokers into it, and only one of an organisation's hubs can carry the organisation's plain name; before, the policy rendered that one name, `<customer>-simple-oidc`, as `targets.<target>.connectorId` and `identityProviders.<target>.connectorId` on every hub, so a target's second hub of the same organisation rendered a connector that, on the target's Dex, trusts the first hub, and the comparison marked the connector the second hub actually exchanges through as *differs by input: installation.federation*. Now the record carries, per target, the hubs of the hub's organisation that broker into it (`installation.federation.targets[*].hubs`: the cluster-token broker of every portal on record that lists the target, the registry's hub first where it is one, then by name), and the policy names two connectors as templates over the hub's record — `federation.connector.first`, `<customer>-simple-oidc`, for the target's first hub, and `federation.connector.further`, `<customer>-<hub>-oidc`, for every further hub of the same organisation. A target this hub alone brokers into, and every first hub's, render as before; a list that does not name the hub is refused at plan time. The golden `second-hub` renders an organisation's second hub into a target its first hub brokers into as well, next to a target it alone brokers into. The customer-portal definition renders no connector.

- `verify_capability {content: true}` and the dry runs answer, per file, the file on record next to the file as the plan writes it, and place every difference on its line of each side, so a reader draws one diff per file with each difference annotated where it sits. `files[].current` is the record as the caller reads it, omitted for a file the record lacks or when the content was not asked for; of a file SOPS encrypted it is shown with SOPS's block dropped and the leaves under its `encrypted_regex` reading `<encrypted>` in place of the ciphertext, every other line as it is on record — and `files[].content` the same way where the plan kept ciphertext of a shared file, so both sides compare. `differences[].line` and `differences[].currentLine` are the 1-based lines of the leaf in `content` and `current` as shown (a mapping entry's key line, a sequence entry's `- ` line), omitted on a side that lacks the leaf. Nothing else in the answer changes.
- `list_installations {summary: true}`: the states and the last actions alone, without the record, the inputs on record, the portals and the federation facts — a third of the reads, for a fleet overview such as the Dev Portal's Installations page. The answer says `summary: true`; the default answer is unchanged.

### Added

- The terminal Action state *removed*: when the fileset an action wrote is gone from the repositories' default branch again — the definition's enabled marker absent after the merge, a revert by hand — the next read moves the action to *removed*, the stage's message naming the file and the repository. The fleet's Kustomization over the extras tree does not prune (`Prunes: false` on the definition's registry entry), so the record names the objects the definition rendered on the installation that stay until a person deletes them — the HelmReleases the definition's probes name first (deleting one uninstalls its chart), then every manifest among its files by kind, namespace and name (`status.orphans`; `platformctl action get` prints them) — read from the render of the inputs on record: the manager deletes nothing on the cluster. The review's thread is told; `list_installations` reads the files' state (*not enabled*) with `lastAction.result: removed`; a removed action is neither watched, merged nor denied. The commit records each installation's marker on the spec (`spec.markers`, `owner/repo:path`); for a record from before, the marker is found in the stage's pull request to the definition's marker repository. The CRD declares the new fields and the state. Scenario test: an enablement merged through the manager and reverted by hand.
- `watch_action {action}` on the live registration: the rollout watch of a merged action, as the person calling. The manager holds no token beyond a call, so the watch is a call — the portal's page, `platformctl action watch <name>`, an agent — never a loop or a schedule. It reads the Flux objects the definition names on the installation rolling out (the HelmReleases with their Ready condition and the revision they report) through muster's kubernetes tools with the caller's forwarded token and answers the picture, recorded on the Action (`status.rollout.installations[].objects`, `watchedAt`, `watchedBy`); once every one is Ready it runs the definition's probes — the live dimensions as the person and, new on the live side, the anonymous HTTP probes direct — and the stage moves to *enabled* (nothing red), *waiting for the customer* (the customer's own action is the only thing open) or *failed* (a probe is red, named); `status.probes`, `status.result` and `rollout.finishedAt` are written, and the report — pull requests, rollout per object, each probe by mark, the open customer actions, what follows — goes into the review's thread (`POST /reviews/{id}/results` with the manager's projected ServiceAccount token; `reportedAt` on the stage, a report the gateway did not take is posted by the next call, one the gateway lost is said so). Anyone signed in may watch: the reads are theirs and the state follows the picture whoever read it. An action *waiting for the customer* or *enabled* is re-read; the customer's action done flips it to *enabled* — through `watch_action` or `verify_installation`, whose recorded result now moves the action's result the same way. `platformctl action watch <name>` prints the picture; `get_info.live.tools` lists both tools of the surface. Not compared: the merged commit's SHA is not on record (gitops-commit's merge answers none), so a HelmRelease's revision is reported, not held against the pull requests; the extras' Kustomizations are not named by the render and are not watched.

### Changed

- `merge_action` no longer verifies a stage itself: at a stage whose pull requests are merged and whose watch has not said *enabled* it refuses, naming the stage's state, `watch_action` and the stage that waits behind it — a stage *rolling out* is the watch's to carry, one *waiting for the customer* holds the wave until the customer's action is done. Before, the call after the merge ran `verify_capability` as the actor and either completed the stage or stopped the wave on a red anonymous probe. The stop is the watch's now, with the same shape: that stage *failed*, the stages after it not started, their pull requests open, the result naming where and why. `MergeResult` lost `verified` and `stopped`; the messages after a merge name `watch_action`.
- The Team review in Slack is one line: who asks to enable or reconcile which capability on which installation (a customer installation, a wave and the installations a wave skips marked as before). The pull request count, the files by change, the generated secrets by name, the rotations and the explanation of the buttons are gone from the text: the pull requests are the review's links, and each pull request's body and the Action's `spec.change` carry the change in full.

### Fixed

- A reconcile of an installation the manager enabled keeps its encrypted files and rotates nothing. The plan compares a secret file on record with the render as YAML, the values the record holds encrypted (the fields under the repository's `encrypted_regex`) and the values the commit fills in left out — SOPS keeps every key, the metadata and every other field in plaintext, so the manager still decrypts nothing: same skeleton → the file is `unchanged`, the values in it stand and its generated names read `kept` (`generatedSecrets[].kept`); nothing is written for it. Before, a secret file on record always read `update` (the bytes differ) and the plan-time frozen check rotated every generated name frozen in a file the definition owns — on an enabled installation that is every name, so a reconcile with nothing to change rewrote every Dex client secret, OAuth encryption key, registration token and Valkey password, and a wave would have done it on every installation at once. A name rotates only when a file of the name has to be written — a file to create, an existing file whose plaintext skeleton the render changes (a field added to its template), or a plain file to write carrying a key pair's public half — and the dry run names that file (`generatedSecrets[].forcedBy`; `platformctl` prints `rotates: <name> (forced by <file>)`, the pull request `rotated … (forced by <file>)`); the kept files sharing the name are rewritten with it and every other name they hold rotates with them, as before. A plain file kept on record with a key pair's public half is rewritten when the pair rotates. A secret file on record the plan does update — its skeleton changed — is written anew with the values it asks for; before, one holding only supplied values was left out of the pull request. Unseen by the comparison: a literal the render changes under an encrypted field, which the record holds encrypted. Scenario tests: a reconcile after the enablement shows every file unchanged, every name kept and a commit with nothing to do, a plain file's change the one file of the pull request; a field the record lacks rotates that file's names and the files sharing them; a Dex client Secret absent from the record rotates the client secret, forced by the new file, and the credentials file with it.
- Every pull request the manager opens is titled in conventional-commit form — `feat(<installation>): enable <capability> (<action>)` for an enablement, `fix(<installation>): reconcile <capability> (<action>)` for a reconcile, a wave's per-installation pull request the same with its stage after the action id — so the GitOps repositories' `semantic-pull-request` check passes as opened; before, `<kind> <capability> on <installation> (<action>)` failed it on every pull request and the merge waited for a person to retitle them. The action id stays in the title and body; a test holds the title to the check's default pattern and types.
- A generated value frozen in an encrypted file on record is found by the plan before any write, and the commit rotates it. The manager decrypts nothing, so a secret file on record holds values no new file can share; an installation that carried a server's `oauth-credentials.enc.yaml` from a hand-made setup had `mode: commit` open the configs repository's pull request and then fail in the management-clusters repository with `generated value exists in an encrypted file already in the repository`, the Dex client's new Secret needing the same value. Now the dry run lists every generated secret's `frozenIn` (the files on record that hold it) and marks it `rotates` when a file to create needs it: the commit draws a new value and writes it into every file of the name — the existing file rewritten and encrypted anew, and every other value that file holds rotated with it down to the files sharing those (the Valkey password into the Valkey Secret). `platformctl` prints `rotates: <name> (<files>)` with what it means for the installation (both sides roll; the client is unusable between the two rollouts); the review text and `spec.change` say `rotates …`; the Action records the rotated names in `status.rotated`; the pull request names them. A frozen value needed by no new file keeps its file untouched. A value frozen in a file with several owners cannot rotate and refuses the commit before any write, naming the file (`commitRefused` in the dry run).
- A commit that fails after opening pull requests closes them itself as the person, branches deleted, and records them `closed` with the reason on the failed Action; before, they stayed open with nobody able to close them through the manager (`deny_action` refused a failed action). `deny_action` takes a failed action too: any pull request the failure could not close is closed, the reason recorded, the action stays failed; a second denial is refused.

### Changed

- The chart serves the live path and registers it with muster as two switches: `live.enabled` turns the path on in the Deployment on its own, `muster.liveServer.enabled` renders the registration and refuses to render without the path, naming both keys. The path goes on in a release of its own and the registration in the next, because muster probes a registration once and a probe that reaches the previous pod — still behind the Service while the release that turns the path on rolls out — finds no path there and leaves the registration failed until it is restarted (giantswarm/muster#1295); against an answering path the probe reads *Auth Required*, and *Connected* once the first person's session connects. Before, the registration and the path came with the one switch and the same release.
- `live.jwksURL` is an `https://` URL: the key set is read over TLS only (the JWKS client refuses anything else on every fetch, the private-IP allowance included), so a plain-`http://` URL is refused at start-up and by the chart with a message naming the allowances that exist — `live.allowPrivateIPJWKS` for a private address, `live.caSecret` for a private CA — instead of every token being refused later with `JWKS URI must use HTTPS`. The values and the flag say so; `live.allowPrivateIPJWKS` is documented as the SSRF guard's allowance, not the transport's.
- The muster scenario of the live registration creates the registration the way the chart's two releases do — the path answering first — and reads the registration *auth_required* at creation and *connected* after the person's session; the instance log carries no "legacy SSE server" verdict.
- The `agent-platform` definition asks a person for one thing: `modelServing.enabled` (default false), which renders the meta chart's serving slice on the 4 chart line. Every other former input is derived — from the record (`installation.*`, now with `portals` and `federation` read from the portals' app-configs: which portals sign people in, whose broker exchanges tokens into the installation, which installations its muster brokers for), from `policy.yaml` (the components an organisation's installations run, whose model key it is, the gateway's shape, the hub connector, the Teleport cluster) or from the shared template — or is no option: what the fleet carries there is a named migration in `removals.yaml`. The schema shrank from 47 typed leaves and five required choices to the record and one checkbox because the platform has few options today — installed or not, serving models or not — and everything else was a fact or a fleet decision typed by hand. Three facts of that record and policy: `installation.private` means reached through Teleport — a portal on record reaches the installation's Kubernetes API through the tunnel on the portal's host (`kubernetes-<name>.agent-platform.svc.cluster.local`), which is what the private-address flags of muster and the MCP servers and a hub's tunnel follow; `managementCluster.private` of `config.yaml.patch` is not read. Every generated secret value is named per installation (`<installation>-muster-dex-client-secret`, …): a wave commits several installations of one organisation into one pull request and the commit step draws one value per name, so a shared name would have been a shared client secret — the portals' Dex client id stays the constant `backstage`, its secret is each installation's own (a test holds it). The agent sandbox is no component of the definition; the one installation running it stops (`removals.yaml`, M13).
- `enable_capability`, `reconcile_capability` (one installation and the wave), `verify_capability` and `platformctl installation enable|reconcile|verify` take every definition of the registry — `customer-portal` as `agent-platform` — through the definition's own `Parse` and `Render`; the plan, the verify and the commit hold nothing of one definition. The installation facts a definition receives are the ones its schema names under `installation`, from the record, the registry (`region`, `pipeline`) and the capabilities' enabled states (`agentPlatform`, `customerPortal`); a fact the schema does not name is not passed.
- The portal's plugin signing keys render as one generated key pair (`backstage-plugin-keys`, kind `keypair-es256`, gitops-commit v0.7.0): the commit step draws an ECDSA P-256 pair once, the private half into the secret file as PKCS #8 PEM, the public half as SPKI PEM — in place of two unrelated base64 values.

### Added

- The wave: `reconcile_capability` with `mode: commit` over a set (`installations`; empty: every installation of the registry) is one action with one approval — one dry run listing the pull requests per installation and the installations *skipped: not opted in*, one review listing the targets in the rollout order and the skipped, one Action carrying every installation's state (`spec.skipped`, `status.rollout.installations[]`, `installation` on every recorded pull request), the pull requests per installation on `platform/<action>/<installation>`. `merge_action` rolls the wave out one stage per call: it merges the first installation's pull requests once green; the next call verifies the installation rolling out (`verify_capability` as the actor) and, green, merges the next; a red probe stops the wave — the installation *failed*, the stages after it not started, the remaining pull requests open, the result naming where and why. The default order is Giant Swarm's test installations, the hub, then the customers; `order` on the dry run and the commit names another. A wave carries no supplied secret values: a target whose supplied secret files are not on record refuses the wave before any write. A single-installation action is a wave of one: the call after its merge verifies it and moves it to *enabled*.
- `list_installations` answers the per-installation state of a running wave (*rolling out* for its installations, *failed* for the one a red probe stopped it at).
- `platformctl installation enable|reconcile … --commit`: the manager's `mode: commit` — for one installation the action, for `reconcile --all` the wave over the set — the supplied secrets the plan names read from `--secret <field>=@<file>`, `<field>=env:<NAME>` or `<field>=-` (stdin) and sent once — never printed, never taken from the command line (a value typed there is refused naming only the field); `platformctl installation verify <installation> <capability>`: the definition's features with their marks and dimensions, every difference with its file, path and driving input or drift, every probe with its requests; `platformctl action approve|deny|merge <name>`: the review's tools called as you, `deny` with its `--reason`. `--output json` on all of them prints the manager's answer as it is.
- The `customer-portal` definition (`render/customerportal`, `definitions/customer-portal/`): an installation's own developer portal rendered into `management-clusters/<name>/extras/backstage/` of its management-clusters repository over the fleet's backstage bases — the kustomization with the portal's directory and, with the agent platform enabled, the agent-platform definition's Component; the portal's directory with the chart's release range and the HelmRelease's values sources patched over the main base, the app-config and values ConfigMaps, the Secrets `user-secrets-backstage`, `plugin-keys-backstage`, `github-app-credentials-backstage` (github on) and `dex-client-backstage` in plaintext with generated placeholders, and the tunnel's SPIFFE bundle reference (tunnel on). The installation's dex-app configmap patch has one owner: without the platform this definition renders it with the portal's Dex client; with it the agent-platform definition carries the same entry through its new `portal.domain` input, both built by `render.PortalDexClient`. Probes as data (release, pods, home page, the sign-in's redirect to Dex, Dex's answer to the portal's client, the Secrets, the platform's fragment) and the anonymous probes `portal-root`, `portal-oidc-start` and `dex-auth-request`. `list_installations` answers for it (marker: the portal's app-config in the management-clusters repository; `Capability` names the repository its marker is read from), `get_info` lists both definitions with their schemas and features from the registry (`installations.Capabilities`), `platformctl template` renders the shape `customer-portal`. `enable_capability`, `reconcile_capability` and `verify_capability` list it in their `capability` enum and refuse it, naming the tool that takes it and that its reconcile is part 2.
- The approval of an action through klaus-gateway's Team review: `mode: commit` posts one review to the capability-owning team's channel (`approvals.team`, `approvals.channel`; the notice channel `approvals.noticeChannel` told for a customer installation) naming the actor, the pull requests and the change, with the receipt on the Action; `approve_action` (the Approve button, called as the clicking member) submits an approving review on every pull request with that member's token and refuses the actor; `deny_action` records the reason, closes the pull requests as the member and moves the Action to *denied*; `merge_action` merges the approved pull requests as the actor in dependency order once their checks are green, moves the Action to *rolling out* and posts the outcome into the review's thread — before the decision it posts the review when none is up and re-posts one the gateway no longer holds. The requests carry the pod's projected ServiceAccount token (`approvals.audience`); without `approvals.gatewayURL`, `mode: commit` is refused.
- `denied` in the Action CRD's `status.state`; `head`, `headSha` on the recorded pull requests; `customer` and `change` in the spec; `noticeChannel`, `postedAt` on the approval; the actor's email.
- The commit step lists every include in its kustomization: `./agent-platform/` and the MCP servers under `resources:` of the installation's `extras/kustomization.yaml`, the portal's fragment under `components:` of the portal host's `extras/backstage/kustomization.yaml`. The dry run reads each kustomization as the person and shows it among the files (update, unchanged, or unknown when it is absent or unreadable — a kustomization other owners write is never created) and every include with its list and change; the commit writes the edited kustomization with the repository's other files and, as for any file, refuses while one is unknown.
- `enable_capability` and `reconcile_capability` with `mode: commit` for one installation: the opt-in gate (`management-clusters/<name>/platform-manager.yaml` read as the person at call time; absent, `optIn: false` or unreadable refuses naming the installation and the file and records the refusal as an Action in state *refused*), the Action created in *pending approval*, the files rendered with the supplied `secrets` (by field, never in the Action, a log or an answer), the secret files encrypted through gitops-commit's `sopsenc` for the repository's `.sops.yaml` recipients, and the pull requests through gitops-commit as the person in dependency order on `platform/<action>/<installation>` with the action id in every title and body; a failure on the way moves the Action to *failed* with the pull requests opened so far. The approval, merge and rollout follow in a later version.
- `refused` in the Action CRD's `status.state`.

### Changed

- The live surface trusts a list of token audiences: the chart value `live.audiences` (list) replaces `live.audience` (string; removed, the chart is 0.x), and `muster.liveServer.requiredAudiences` renders `spec.auth.requiredAudiences` on the live `MCPServer` — the audiences muster requests at login, so every forwarded token carries them whichever client the person signed in with. The server trusts the union of the two lists (`LIVE_AUDIENCES`, `--live-audiences`, comma-separated); an empty union refuses to render and to start the live surface, since an empty list would accept every audience. `get_info.live` reports `audiences`. A person's ID token names the client they signed in with — the platform's own, a developer portal's — so a hub with several sign-in clients accepted only one of them before.
- The managed model key of kagent is rendered as `secrets/kagent-anthropic-key-secret.yaml` (the Secret keeps its name `kagent-anthropic-key`): a secret file's name carries `secret` or `credential` so that the commit encrypts it.
